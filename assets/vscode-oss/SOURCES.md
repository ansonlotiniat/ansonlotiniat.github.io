## Core workbench

- Project: Microsoft `vscode`, the open-source `Code - OSS` repository.
- Version/tag: `1.131.0`.
- Tag commit: `3a03d6f72d628a7741c29f456b4ddbb5ae68502c`.
- Source: <https://github.com/microsoft/vscode/tree/1.131.0>
- Build target: official `vscode-web-min-ci` Gulp target on Node `24.18.0`.
- Licence: MIT; retained in `LICENSE.txt`.
- Third-party notices: retained in `ThirdPartyNotices.txt`.
- Build output: `out/`, `extensions/`, and the production browser dependencies in `node_modules/`. `bootstrap.js` is the local embedder layer and calls the official public web `create()` entry point with a trusted, disposable multi-root workspace.
- The pristine 17,646,033-byte upstream core has SHA-256 `525cfaf13d4f2310d5c76546f3f078a7535baf4799135db092c830462fc2c943`. The local 17,646,363-byte core has SHA-256 `3899e6fb10b531694b79b7d40255dba286704683f17e918d63f3ed103416653a` and differs at exactly two documented integration points: it awaits the public-workspace seed after registering Code - OSS's own `tmp:` provider, and registers the matching `tmp:` file/text search provider during search-service construction. Explorer, Monaco, tabs, Quick Open, search results, and the rest of the workbench remain the official implementation.

The installed Microsoft Visual Studio Code application was used only as an explicitly authorized visual reference. Its proprietary distribution files and signed application bundle were not copied into this web build.

## Embed startup

- The parent page declares the explicit `assets/vscode-oss/index.html` iframe as an eager static resource so Code - OSS starts during HTML parsing, before the window is opened. Naming the file is essential: a relative directory URL resolves to an HTTP index document on GitHub Pages but to a directory listing when the portfolio itself is opened from `file://`.
- `host.js` renders the authorized captured state independently, posts separate visual-ready and runtime-ready signals, and answers repeated parent readiness probes. The parent also checks same-origin DOM state, accepts a structured runtime-error signal, and exposes a bounded retry path if no visual state appears within six seconds.
- HTTP and GitHub Pages use `bootstrap.js` as a native module and preload the 17,646,363-byte pinned core with the two documented workspace hooks. This remains the primary and fully enabled Code - OSS path.
- Chrome assigns local files opaque origins and blocks `type="module"` imports between them. For direct double-click / `file://` use only, `index.html` therefore selects `workbench.file.js`, a classic IIFE compatibility build generated with esbuild 0.28.2 from the same official core plus the local embedder. Its startup-only keyboard-layout module import is replaced by the core browser-event fallback because local module fetching is unavailable. The editor, Welcome page, and genuine untitled Monaco documents work without a server; the web-extension worker remains unavailable under Chrome's opaque local-file origin.
- `workbench.file.js` is 17,610,057 bytes with SHA-256 `f83b6cba2c3864ea6cbd087aebaffa9df0ef82b74b6846c9d7efc99c8f7c16f6`. It is not requested on HTTP/GitHub Pages, so the normal web path does not download a duplicate core.

## Public source workspace

- `workspace-data.js` is a generated 123-file, 698,537-byte public snapshot with SHA-256 `0f5e722b8891cf283ad8a16bb7d42f8ccd7719ff68ec6d7b07d2b1a84092dad7`. Remote files are pinned to seven explicit public Git commits; selected current-site files are read from this working tree. Exact mappings, licences, and privacy boundaries are in `WORKSPACES.md`.
- `workspace-search.js` is the 7,018-byte in-memory file/text search provider with SHA-256 `215c6ed37394247a0b5d365037f9b6515a31c9fd4df78a0eae03456a3067d488`. It restores Quick Open and Search for the `tmp:` scheme without replacing Code - OSS's search UI.
- `scripts/build-vscode-workspace.mjs` is the reproducible builder. It fetches pinned text sources, generates the workspace payload, verifies/installs both narrow core hooks, and regenerates the local-file compatibility bundle.

## Captured initial state

The initial welcome overlay is a clean-room transcription of the user's visible 1152×768 VS Code window on 2026-08-03. It records only visible interface state: Traditional Chinese labels, the five visible Recent entries and paths, the two walkthrough cards, installed-tool entry names, editor actions, and status-bar labels. It does not copy file contents, credentials, extension storage, account state, terminal output, or hidden recent entries.
